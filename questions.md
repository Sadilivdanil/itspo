# Вопросы для самопроверки

1. Какие критерии вы использовали при разделении монолита на микросервисы (или при проектировании сервисов)?

Критерий функциональной ответственности (Single Responsibility): Система разделена по бизнес-доменам. Сервис starter (каталог продуктов) изолирован от сервиса orders (оформление заказов), так как они имеют разный жизненный цикл и логику.

Изоляция данных и независимое масштабирование: Сервис каталога товаров подвержен более частому чтению (просмотр товаров пользователями), поэтому он вынесен отдельно, что позволяет масштабировать его независимо от сервиса заказов.

2. Почему вы выбрали именно этот стек технологий (язык, БД, протоколы)?

Язык Python и фреймворк FastAPI: Выбраны за счет высокой скорости разработки, встроенной асинхронности (async/await) и автоматической генерации документации Swagger. Это обеспечивает высокую производительность микросервисов при обработке сетевых запросов.

База данных In-Memory: Использована для упрощения архитектуры в рамках учебного проекта, ускорения работы и демонстрации логики работы микросервисов без накладных расходов на развертывание полноценной СУБД.

Протоколы REST (HTTP) и gRPC: REST используется для внешних запросов клиентов через API Gateway (Nginx) благодаря его простоте и универсальности. Внутренний gRPC (специфицированный в архитектуре) выбран для высокопроизводительного, типизированного межсервисного взаимодействия с минимальными задержками.

3. Как ваши сервисы справляются с ошибками (retry, circuit breaker, graceful degradation)?

Валидация и обработка исключений: В коде orders реализованы блоки try-except с использованием библиотеки httpx для перехвата сетевых ошибок.

Graceful Degradation (Снижение функциональности): При недоступности основного сервиса продуктов (starter), сервис заказов не падает целиком, а корректно возвращает пользователю ошибку HTTP 503 (Сервис временно недоступен), изолируя сбой внутри системы.

4. Как организован деплой и обновление вашей системы без простоя (Zero Downtime)?

Оркестрация в Kubernetes: За счет использования манифестов Deployment со стратегией RollingUpdate.

Настройки maxSurge: 1 (создавать один дополнительный под при обновлении) и maxUnavailable: 0 (не удалять старые поды, пока новые не заработают) гарантируют плавную замену версий кода.

Контейнеры не включаются в балансировку трафика до тех пор, пока их эндпоинты /health не ответят успешным кодом 200 через readinessProbe.

5. Что было самым сложным в интеграции всех компонентов вместе?

Настройка сетевого взаимодействия и путей: Синхронизация маршрутов на API Gateway (Nginx) с реальными эндпоинтами микросервисов, а также настройка корректного DNS-разрешения имен контейнеров внутри сети Docker Compose и кластера Kubernetes (передача URL через PRODUCTS_SERVICE_URL).

Отладка CI/CD пайплайна: Настройка правил статического анализа (pylint/flake8) в GitHub Actions, чтобы автоматическая проверка кода учитывала специфику структуры папок проекта и не блокировала сборку Docker-образов.

6. Что бы вы улучшили, если бы у вас был еще месяц?

Красивый интерфейс (Фронтенд): Сейчас проект работает только как бэкенд-API, и отправлять запросы нужно через терминал. Я бы дописал простую веб-страницу (интерфейс), чтобы обычные пользователи могли заходить, смотреть каталог товаров и кликать по кнопке «Купить» в браузере.
