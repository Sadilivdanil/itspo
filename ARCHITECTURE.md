# ARCHITECTURE.md — Спецификация системы (products-s14)

## 1. Обзор архитектуры
Система спроектирована как микросервисная архитектура, состоящая из двух независимых функциональных сервисов и одного компонента маршрутизации (Шлюза). Взаимодействие между компонентами изолировано внутри виртуальной сети, а развертывание адаптировано как для локальной разработки (Docker Compose), так и для промышленной оркестрации (Kubernetes).

## 2. Микросервисы

### 2.1. starter (products-svc-s14) - Основной сервис
* **Назначение**: Управление каталогом товаров и предоставление информации о ценах.
* **Протокол**: REST (внешний) / gRPC (внутренний, сервис: `ProductsService`, пакет: `products.v1`)
* **Порт**: `8223`
* **База данных**: In-Memory (список объектов в оперативной памяти)
* **Структура сущности (Product)**:
  * `id` (int): Уникальный идентификатор товара.
  * `name` (string): Наименование товара.
  * `price` (float): Обязательное поле стоимости товара.
* **Эндпоинты**:
  * `GET /api/products` - Получение полного списка доступных товаров.
  * `GET /health` - Проверка жизнедеятельности (Liveness/Readiness Probe).

### 2.2. orders - Дополнительный сервис
* **Назначение**: Оформление заказов пользователей и расчет итоговой стоимости через межсервисные запросы.
* **Протокол**: REST
* **Порт**: `8224`
* **Межсервисное взаимодействие**: При создании заказа выполняет синхронный RPC/HTTP-запрос к сервису `starter` для проверки существования товара и валидации его цены.
* **Переменные окружения**:
  * `PRODUCTS_SERVICE_URL` - Сетевой адрес API каталога товаров.
* **Эндпоинты**:
  * `POST /api/orders` - Создание нового заказа (принимает `product_id`).
  * `GET /health` - Проверка жизнедеятельности (Liveness/Readiness Probe).

## 3. Компонент шлюзования (API Gateway)
* **Реализация**: Обратный прокси-сервер (Reverse Proxy) на базе **Nginx**.
* **Внешний порт**: `8085` / `8080` (в зависимости от среды развертывания).
* **Логика путей и маршрутизация**:
  * `/api/products` перенаправляется на внутренний адрес `products-container:8223`
  * `/api/orders` перенаправляется на внутренний адрес `orders-container:8224`
  * `/health` общая проверка доступности самого шлюза.

## 4. Спецификация развертывания в Kubernetes (k8s)
Для обеспечения высокой доступности и концепции **Zero Downtime Deployment** (развертывание без простоя) система манифестов настраивает:

* **Стратегия обновления (RollingUpdate)**: Параметры `maxSurge: 1` и `maxUnavailable: 0` гарантируют, что во время обновления старые поды не удаляются, пока новые контейнеры не пройдут проверку готовности.
* **Масштабирование и репликация**:
  * `products-deployment` - Запущено **3 реплики** (поды `products-svc`) для распределения нагрузки на каталог.
  * `orders-deployment` - Запущено **2 реплики** (поды `orders-svc`) для отказоустойчивости цепочки заказов.
* **Сетевые службы (Services)**:
  * `products-container` (ClusterIP, порт `8223`) - выступает в качестве внутренней DNS-записи для кластера. Через него сервис заказов связывается со стартером по URL: `http://products-container:8223/api/products`.
  * `orders-container` (ClusterIP, порт `8224`) - балансировщик трафика для сервиса заказов.
* **Проверки мониторинга (Healthchecks)**:
  * `livenessProbe` - Опрашивает эндпоинт `/health` каждые 10 секунд. При сбое Kubernetes автоматически перезапускает зависший контейнер.
  * `readinessProbe` - Исключает под из сетевой маршрутизации, пока приложение внутри контейнера полностью не инициализируется.

## 5. Конвейер автоматизации (CI/CD Pipeline)
Автоматизация качества и сборки реализована через **GitHub Actions** (`.github/workflows/ci.yml`) и состоит из 4 последовательных этапов:

1. **Lint (Линтинг)**: Статический анализ кодовой базы с помощью `flake8` (синтаксис PEP8) и `pylint` (качество архитектуры кода) в каталогах `orders/` и `starter/`. Проверяет код перед сборкой с проходным порогом `--fail-under=4.0`.
2. **Test (Тестирование)**: Автоматический прогон модульных и интеграционных тестов в изолированном окружении с помощью фреймворка `pytest` над директорией `tests/`.
3. **Build (Сборка образов)**: Тестовая сборка Docker-образов через `docker/build-push-action@v4` для верификации корректности инструкций в `Dockerfile`.
4. **Publish (Публикация артефактов)**: Формирование отчета об успешном прохождении конвейера (`report.txt`) и его сохранение на серверах GitHub (`upload-artifact`).
